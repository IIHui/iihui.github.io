cocoapods组件名

CocoaPods组件名（Pod Name）原则上不能包含英文点号，同时也不能以点号开头。CocoaPods在生成对应的 Swift或Objective-C模块（Module）时，需要遵循编程语言的标识符命名规则。这些规则通常只允许字母、数字和下划线，因此像点号（.）和连字符（-）这类符号是不被允许的。

如果一个Pod的名字里包含了这些符号，CocoaPods在生成模块名时，会自动将它们替换为下划线（_）。但为了避免潜在的混淆和问题，组件命名时最好遵循以下原则：

  • 只使用：字母（a-z, A-Z）、数字（0-9）和下划线（_）。
  • 使用：驼峰命名法或下划线分隔。

CocoaPods的Module Name和podspc中定义的spec.name是两套系统。spec.name是给CocoaPods包管理器内部使用的「身份证」，而 import语句使用的是面向编译器的模块名。

# podspec的定义
spec.name         = "LC09.09_xxx" 

# import使用的语法，即需要添加下划线
LC09_09_xxx

Xcode和Swift编译器要求模块名必须是C99扩展标识符，即只能包含字母、数字和下划线（_），且必须以字母或下划线开头。所以spec.name中的点号（.）是不被允许的。为了让编译通过，CocoaPods会自动将spec.name中所有非法字符（如.、-等）替换为下划线（_），生成一个合法的模块名。

如果不想使用自动生成的名字，可以在podspec中可以通过spec.module_name属性来指定一个更友好的模块名，按下面设置后可以直接import LC09_09_xxx：

Pod::Spec.new do |spec|
  spec.name         = "LC09.09_xxx"
  # ... 其他配置 ...
  spec.module_name  = "YYY" # 自定义一个简洁合法的模块名
end

pod update

在podfile文件中使用:path =>依赖本地组件的低版本时，然后执行pod update时出现如下错误：

Errno::ENOENT - No such file or directory @ rb_sysopen - /Users/xxx/Downloads/xxx/Pods/Local Podspecs/Router.podspec.json /Users/xxx/.rvm/gems/ext-ruby-4.0.6/gems/cocoapods-core-1.17.0/lib/cocoapods-core/specification.rb:690:in 'IO.read' /Users/xxx/.rvm/gems/ext-ruby-4.0.6/gems/cocoapods-core-1.17.0/lib/cocoapods-core/specification.rb:690:in 'Pod::Specification#checksum' /Users/xxx/.rvm/gems/ext-ruby-4.0.6/gems/cocoapods-core-1.17.0/lib/cocoapods-core/lockfile.rb:543:in 'block in Pod::Lockfile.generate_checksums'

这个错误是CocoaPods处理本地组件 (:path) 时，因缓存或状态不一致导致的。CocoaPods在Pods/Local Podspecs/目录下找不到（或无法读取）Router.podspec.json这个文件。这个文件是CocoaPods在pod install时生成的本地Podspec缓存，用于计算校验和 (checksum)。当这个缓存缺失或损坏时，pod update就会报错。

临时解决方案是将需要本地依赖的组件的podspec文件手动复制到工程的Pods/Local Podspecs/目录下，然后执行pod update命令。也可以使用如下命令删除缓存和依赖文件：

rm -rf Pods Podfile.lock

实际上，最简单的方式是使用pod install，而不是使用pod update命令。因为，CocoaPods在执行 pod update 时，并不是一口气完成的，而是分为三个阶段：

  1. 解析阶段：读取Podfile和Podfile.lock，计算新的依赖版本。
  2. 校验阶段：在这个阶段，CocoaPods会立即读取Pods/Local Podspecs/\*.podspec.json文件，计算当前沙盒（Pods文件夹）中各组件的checksum（校验和），用来和Podfile.lock中的旧校验和做比对，判断本地缓存是否被篡改过。
  3. 写入阶段：下载/复制新代码，并重新生成Pods/Local Podspecs/下的缓存文件。

当Router.podspec.json文件不存在时，CocoaPods在第二阶段就直接抛出Errno::ENOENT异常并终止了进程，还没走到第三阶段（写入/生成新文件）。

CocoaPods的设计者假设沙盒（Pods文件夹）一旦通过pod install 生成，就永远处于完整状态。pod update 是一个增量更新命令，它默认信任现有沙盒的完整性，不会在校验失败时自作主张去创建缺失文件，因为如果文件缺失，说明沙盒状态已损坏，最安全的做法是报错退出，让开发者手动修复（即执行完整的pod install）。

所以只要修改了:path 指向的本地组件代码或.podspec 版本号，永远执行 pod install，而不是 pod update。

实际上，pod install和 pod update的核心区别在于：pod install用于安装并锁定版本，而pod update用于更新到新版本。它们的核心区别如下：

特性 pod install pod update
主要用途 安装新库，或添加/删除已有库 更新现有库到更新的版本
对Podfile.lock 的处理 尊重并锁定：使用其中记录的版本，不会检查更新 忽略并更新：忽略其中版本，查找符合 Podfile 的最新版本
对新Pod的处理 查找并安装符合Podfile的最新版本 会更新所有Pod，风险较高，不推荐用于添加新Pod
使用场景 首次设置、修改Podfile` 后、拉取同事代码后 主动、有目的地升级某个或所有Pod

Podfile.lock文件是实现上述差异的关键。它记录了每个Pod当前使用的确切版本，保证了项目依赖的一致性。当运行pod install时，CocoaPods会以此文件为准，确保所有团队成员或部署环境的依赖版本完全一致。

expected attach.dylib to exist

从官网下载PyCharm 2026，接着双击并拖到Applications目录（即替换已有的应用），然后使用新版打开项目，调试时出现如下如下错误信息：

Expected: /private/var/folders/ns/9rvphkg1387_4zqncdbkbml80000gn/T/debugpy3185433954253459765/debugpy/_vendored/pydevd/pydevd_attach_to_process/attach.dylib to exist.

临时解决方案是找到PyCharm目录下的attach.dylib文件，即使用如下命令：

find /Applications/PyCharm.app -name "attach*.dylib" 2>/dev/null

然后将找到的attach.dylib文件复制到/private/var/folders/ns/9rvphkg1387_4zqncdbkbml80000gn/T/debugpy3185433954253459765/debugpy/_vendored/pydevd/pydevd_attach_to_process/目录下：

/Applications/PyCharm.app/Contents/plugins/python-ce/helpers/pydev/pydevd_attach_to_process/attach.dylib

这种方式只能临时解决本次编译问题。由于PyCharm的安全机制，这个临时目录会发生变化，即重启PyCharm后，还是会出现一样的错误，因为T的子目录会发生随机变化：

Expected: private/var/folders/ns/9rvphkg1387_4zqncdbkbml80000gn/T/debugpy851305541846591445/debugpy/_vendored/pydevd/pydevd_attach_to_process/attach.dylib to exist.

一直没找到一劳永逸的解决方案，但排查过程中偶然发现，若将debug模式修改为pydevd，则错误会消失。修改mode的方式如下图所示，但这种解决方案也是临时的，因为PyCharm重启后还是会自动将debug模式修改为debugpy。

但从上面find /Applications/PyCharm.app -name "attach*.dylib" 2>/dev/null命令的输出，可以看到attach.dylib文件所在的路径为：

/Applications/PyCharm.app/Contents/plugins/python-ce/helpers/debugpy/_vendored/pydevd/pydevd_attach_to_process/attach.dylib

既然PyCharm的安装目录中是存在attach.dylib文件的，但为什么使用debugpy模式时没有自动复制这个文件到调试的临时目录呢，是不是因为自动复制的目录下不存在attach.dylib文件呢。使用下面命令查找是否存在多个pydevd_attach_to_process目录：

find /Applications/PyCharm.app -name "pydevd_attach_to_process" 2>/dev/null

从上面命令的输出上看，确实存在两个不同的pydevd_attach_to_process目录，这两个目录恰好对应两个调试模式，第一个是pydevd，第二个是debugpy：

/Applications/PyCharm.app/Contents/plugins/python-ce/helpers/pydev/pydevd_attach_to_process

/Applications/PyCharm.app/Contents/plugins/python-ce/helpers/debugpy/_vendored/pydevd/pydevd_attach_to_process

到这里似乎看到了曙光，打开第一个目录后发现确实没有attach.dylib文件。尝试将第二个目录下的attach.dylib文件复制到第一个目录下，然后重启PyCharm，接着使用debugpy模式调试时真的正常了。最后，验证关机重启mac后调试也正常，至此，该问题完美解决😎。
